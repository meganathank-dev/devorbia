# DevOrbia — Technical Architecture v1.0

## 1. Overall Architecture

DevOrbia will use a **modular monolithic MERN architecture**.

```text
                    ┌──────────────────────────┐
                    │        DevOrbia          │
                    │      Web Application      │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │       React Frontend      │
                    │ React + Vite + Tailwind   │
                    │ Zustand + Axios + Router  │
                    └────────────┬─────────────┘
                                 │
                              HTTPS
                                 │
                    ┌────────────▼─────────────┐
                    │      Express Backend      │
                    │        /api/v1             │
                    └────────────┬─────────────┘
                                 │
            ┌────────────────────┼────────────────────┐
            │                    │                    │
            ▼                    ▼                    ▼
      Authentication        Business Logic       AI Services
      Authorization         Services             AI Analysis
      Tenant Isolation      Workflows            Recommendations
            │                    │                    │
            └────────────────────┼────────────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │       Repository Layer    │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │         MongoDB           │
                    │        Mongoose ORM        │
                    └───────────────────────────┘
```

### Why modular monolith?

For the first version, **microservices are unnecessary**.

A modular monolith gives us:

* Easier development
* Easier deployment
* Easier debugging
* Lower infrastructure cost
* Clear module boundaries
* Easier testing
* Easier Antigravity development

If DevOrbia becomes a large production platform later, individual modules can be extracted into services.

# 4. Backend Layer Architecture

The backend follows:

```text
Request
   ↓
Route
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Mongoose Model
   ↓
MongoDB
```

## Routes

Routes define endpoints.

Example:

```text
POST /api/v1/projects
```

Routes should not contain business logic.

---

## Middleware

Handles cross-cutting concerns:

```text
Authentication
Authorization
Tenant Context
Validation
Rate Limiting
Error Handling
```

---

## Controllers

Controllers should be thin.

They:

1. Read request
2. Call service
3. Return response

Business logic should **not** be placed inside controllers.

---

## Services

Services contain business rules.

Example:

```text
createProject()
assignProjectMember()
changeTaskStatus()
requestLeave()
approveLeave()
calculateProjectHealth()
```

This is where authorization-sensitive business decisions can be enforced alongside dedicated authorization utilities/policies.

---

## Repositories

Repositories handle MongoDB operations.

For example:

```text
findProjectById()
findProjectByIdAndOrganization()
findTasksByProject()
findEmployeesByOrganization()
```

This layer helps enforce consistent organization-scoped querying.

# 6. Authentication Architecture

DevOrbia will use:

**Access authentication + refresh/session mechanism**

with secure cookie handling.

Conceptually:

```text
Login
  ↓
Verify credentials
  ↓
Create authenticated session/tokens
  ↓
Secure HTTP-only cookie
  ↓
Authenticated API request
  ↓
Authentication middleware
  ↓
Identify user
  ↓
Identify organization context
  ↓
Authorization
```

The frontend should **not store long-lived authentication secrets in localStorage**.

# 7. User & Employee Separation

This is an important architectural decision.

We should not make one huge document containing everything.

### User

Responsible primarily for identity/authentication:

```text
_id
email
passwordHash
role
status
organizationId
session/security metadata
```

### Employee

Responsible for organization/business information:

```text
_id
userId
firstName
lastName
jobTitle
departmentId
teamId
organizationId
joiningDate
employmentStatus
profileImage
```

This keeps:

**Authentication ≠ Employee management**

# 8. Role Architecture

Initial roles:

```text
SUPER_ADMIN
ORGANIZATION_ADMIN
PROJECT_MANAGER
TEAM_LEADER
EMPLOYEE
```

### Important hierarchy

This is **not** a simple hierarchy where every role reports directly upward.

Instead:

```text
                    DEVORBIA PLATFORM
                           │
                     SUPER ADMIN
                           │
                 Platform administration
                           │
              ─────────────┼─────────────
                           │
                     ORGANIZATION
                           │
                ORGANIZATION ADMIN
                           │
              ┌────────────┼─────────────┐
              │            │             │
         Departments     Projects       Teams
              │            │             │
           Teams       PMs/Members       TLs
              │
          Employees
```

The exact reporting/approval relationships inside an organization will be represented through organization-owned relationships rather than treating Super Admin as part of that chain.

# 9. Super Admin Boundary

This must be permanently clear in the architecture.

**Super Admin is a DevOrbia platform administrator.**

Super Admin:

* Creates organizations
* Grants/revokes platform access
* Activates/deactivates organizations
* Views platform-level statistics
* Manages platform-level administration

Super Admin does **not**:

* Approve employee leave
* Assign company tasks
* Manage company projects
* Manage company teams
* Manage company employees
* View organization internal data unless a deliberately authorized platform-level function requires it

This prevents the platform administrator from becoming an accidental employee of every organization.

# 11. Tenant Isolation

Never trust a client-supplied organization ID.

The backend obtains organization context from the authenticated identity/session.

For example, instead of:

```text
GET /projects/:projectId
```

doing:

```text
findById(projectId)
```

the repository/service layer should effectively enforce:

```text
find project where:

_id = projectId
AND organizationId = authenticatedOrganizationId
```

This protects against:

**IDOR + cross-tenant access.**

---

# 12. Authorization Architecture

We should use multiple authorization layers.

```text
Authentication
      ↓
Role authorization
      ↓
Organization authorization
      ↓
Resource authorization
      ↓
Business-rule authorization
```

Example:

Employee attempts to modify a task.

System checks:

1. Is the user authenticated?
2. Is the user's account active?
3. Is the user an Employee?
4. Does the task belong to their organization?
5. Is the employee allowed to modify this task?
6. Is the requested status transition permitted?

Only then:

**Allow operation.**

# 18. Task Workflow

Initial workflow:

```text
BACKLOG
   ↓
TODO
   ↓
IN_PROGRESS
   ↓
REVIEW
   ↓
DONE
```

Additionally, we should support an **Overdue** concept.

Important distinction:

**Overdue is primarily a time-derived condition, not necessarily a workflow column.**

For example:

```text
Status = IN_PROGRESS
Due date = passed
```

The task can be displayed as:

**In Progress + Overdue**

rather than creating unnecessary workflow states.

This keeps workflow logic clean.

---

# 19. Project Health

Project health should initially be derived from actual metrics.

Inputs may include:

* Completion percentage
* Overdue task percentage
* Critical task status
* Deadline proximity
* Workload
* Progress velocity

Possible result:

```text
HEALTHY
WARNING
AT_RISK
CRITICAL
```

The deterministic calculation should exist **before AI**.

Then AI can provide deeper interpretation.

---

# 20. Leave Architecture

Leave belongs to the organization.

```text
Organization
      ↓
Employee
      ↓
Leave Request
```

Leave request contains information such as:

```text
employeeId
organizationId
leaveType
startDate
endDate
reason
status
approver
timestamps
```

The approval authority should be determined from the organization's configured management/reporting relationships.

**Super Admin is excluded from this organizational approval chain.**

---

# 21. Email Architecture

Don't put email-sending code directly inside controllers.

Use:

```text
Business Event
      ↓
Notification Service
      ↓
Email Service
      ↓
Email Provider
```

For example:

```text
Task Assigned
      ↓
Notification Service
      ↓
Email Service
      ↓
Employee receives email
```

This allows us to replace the email provider later without rewriting business logic.

# 🔒 Architecture Rules We Are Locking

These should be treated as **non-negotiable project rules**:

1. **MERN stack remains the core stack.**
2. **Modular monolith for Version 1.**
3. **Backend is the source of truth for authorization.**
4. **Every organization-owned resource is tenant-scoped.**
5. **Never trust client-supplied organization IDs for authorization.**
6. **Super Admin is platform-level, not organization-level.**
7. **One Organization Admin per organization in Version 1.**
8. **AI recommends; authorized humans make final decisions.**
9. **AI never bypasses RBAC or tenant isolation.**
10. **Controllers remain thin.**
11. **Business logic belongs in services.**
12. **Database operations belong in repositories.**
13. **All external input is validated with Zod.**
14. **No hardcoded secrets or organization IDs.**
15. **No fake dashboard statistics.**
16. **Overdue is a derived condition, not necessarily a workflow state.**
17. **Core deterministic metrics must exist before AI analysis.**
18. **Every major phase must be tested before the next phase.**
19. **Existing working features must not be unnecessarily regenerated.**
20. **No unnecessary technologies or infrastructure.**
