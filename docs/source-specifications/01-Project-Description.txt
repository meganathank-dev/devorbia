3. PROBLEM STATEMENT
====================================================================

Software development organizations often use multiple disconnected
systems to manage their operations.

For example:

- Employee information in one system
- Teams in another system
- Projects in another tool
- Tasks in another tool
- Leave requests through email or manual processes
- Workload tracked through spreadsheets
- Performance tracked manually
- Reports prepared manually

This creates:

- Fragmented information
- Duplicate data
- Poor visibility
- Poor coordination
- Manual workload tracking
- Difficulty identifying project risks
- Difficulty assigning work intelligently
- Difficulty understanding employee capacity
- Difficulty understanding leave impact
- Difficulty identifying performance
- Difficulty managing multiple organizations securely

DevOrbia solves these problems through a centralized,
organization-aware management platform.

5. MULTI-TENANT ARCHITECTURE
====================================================================

Multi-tenancy is a core requirement.

Each organization is an independent tenant.

Example:

Organization A
    - Employees A
    - Departments A
    - Teams A
    - Projects A
    - Tasks A

Organization B
    - Employees B
    - Departments B
    - Teams B
    - Projects B
    - Tasks B

Organization A must NEVER be able to access Organization B data.

Tenant isolation must be enforced at:

- Authentication
- Authorization
- Service layer
- Repository layer
- Database query level

It must NOT depend only on frontend filtering.

Organization-owned resources should contain an organization reference.

Normal resource retrieval should use a combination such as:

resource ID + authenticated organization ID

rather than:

resource ID only

This prevents:

- Cross-tenant access
- IDOR
- Data leakage
- Unauthorized resource retrieval

7. SUPER ADMIN
====================================================================

Super Admin is a PLATFORM-LEVEL role.

Super Admin is NOT an employee of any organization.

Super Admin has NO operational relationship with organization users.

Super Admin does NOT:

- Manage organization employees
- Assign employee tasks
- Manage organization projects
- Approve employee leave
- Manage organization teams
- Manage organization departments
- Control organization workflows

Super Admin's responsibility is limited to platform administration.

Super Admin can:

- Create organizations
- Manage organizations
- Activate organizations
- Deactivate organizations
- View platform-level statistics
- Manage organization access
- Create/assign the organization's initial administrator
- Monitor platform usage

Important:

Super Admin gives an organization access to the DevOrbia platform.

After organization onboarding, the organization operates independently.

====================================================================
8. ORGANIZATION ADMIN
====================================================================

There is exactly ONE Organization Admin per organization.

Organization Admin is the highest operational authority INSIDE
that organization.

Organization Admin can:

- Manage organization profile
- Manage employees
- Create/invite users
- Assign organizational roles
- Manage departments
- Manage teams
- Assign employees to departments
- Assign employees to teams
- Manage organization settings
- View organization dashboards
- View organization analytics
- Manage organization-level operations
- Manage leave administration according to organization policy

Organization Admin cannot:

- Access another organization
- Manage another organization
- Act as Super Admin
- Change platform-level configuration

Organization Admin is independent from the Super Admin in day-to-day
organization operations.

14. ROLE-BASED ACCESS CONTROL
====================================================================

Frontend restrictions are NOT security.

Backend must verify:

1. Authentication
2. Role
3. Organization
4. Resource permissions
5. Ownership/relationship
6. Business rules

Example:

Employee attempts:

POST /api/v1/organizations

Result:

403 Forbidden

Example:

Project Manager changes another organization's project ID.

Result:

Access denied or resource not found according to security strategy.

    ↓

    ↓

- BLOCKED

IN PROGRESS
+
OVERDUE
+
BLOCKED

Status transitions should be validated by backend business rules.

Unauthorized users must not be able to modify status through API

====================================================================
22. TASK COMPLETION
====================================================================

A task is considered complete when its authorized workflow state
becomes:

DONE

However, the system should maintain the distinction between:

- Workflow status
- Deadline state
- Blocking state

Examples:

IN PROGRESS
Deadline passed
=> OVERDUE

DONE
Deadline passed
=> Completed but potentially late

IN PROGRESS
Blocked by another task
=> BLOCKED

This provides accurate project analytics.

====================================================================
23. PROJECT COMPLETION
====================================================================

A project may be considered operationally complete when:

- Required work is completed
- Critical tasks are completed
- Project Manager confirms completion
- Project status is changed to COMPLETED

Project completion should not depend only on percentage.

Example:

A project showing 98% progress but containing one critical unfinished
task should not automatically be considered fully complete.

- Project deadlines
- Task priority
- Dependencies
- Team capacity
- Employee workload
- Existing commitments

The system should identify potential conflicts.

Example:

Employee requests leave:

September 10 - September 14

- 2 active tasks
- 1 critical task
- 1 task due September 11

DevOrbia may show:

HIGH IMPACT

2 tasks are affected.
1 critical task overlaps the leave period.

Important:

The system should WARN about conflicts.

It should NOT automatically reject leave simply because there is a
project impact.
